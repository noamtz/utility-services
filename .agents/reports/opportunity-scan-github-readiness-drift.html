Why the failure repeats

Dependency lands

A PR merges and its issue closes.

Project updates

GitHub's built-in workflow marks only that item Done.

Nothing unlocks

Downstream dependencies exist only in prose and a Wiki diagram.

Label stays stale

No workflow or PIV step changes queued to ready.

Agent diverges

One run overrides the label; another obeys the literal gate and stops.

RUS-03, RUS-05, and RUS-07 plans already documented stale queued labels and proceeded under an inferred owner override. This RUS-08 run interpreted the same ticket wording strictly and stopped. Both behaviors are understandable because the policy never defines how to reconcile a stale label with closed dependencies.

The system gaps

Dependencies are descriptive, not executable

RUS-08's body lists RUS-04/05/06 under “Depends on,” but GitHub reports zero native blockedBy relationships. Automation cannot safely infer readiness from a Mermaid graph or prose forever.

No transition owner exists

There is no .github workflow and no PIV phase responsible for updating readiness after merge. Repository rules also correctly prevent an agent from making unrequested external writes, so drift is the expected result.

There are too many “current state” sources

Issue state, labels, Project Status, Wave, Wiki prose, AGENTS.md, plans, and code all carry overlapping state. The Wiki still says only RUS-01 should be planned; AGENTS.md still says RUS-06+ is unimplemented, although RUS-06 and RUS-07 are merged.

The planning skill has no reconciliation rule

It fetches the ticket but does not define precedence between an explicit planning request, a readiness label, native dependencies, closed dependency issues, and implementation present on main.

Recommended durable changes

GitHub issue model · primary fix

Make native issue dependencies the only readiness source

  • Record the Wiki dependency graph using GitHub's native blocked by / blocking relationships.
  • Delete queued and ready; an open issue with no open blockers is ready by definition.
  • Let the existing built-in Project workflow continue setting closed items to Done.
  • Add a read-only audit only if future drift shows that native relationships are being omitted.
Skill · defense in depth

Teach piv-plan-implementation to reconcile, not merely trust, readiness

  • Fetch blockedBy and issue state together.
  • If any blocker is open, stop.
  • If no blocker is open and the user explicitly invoked planning, proceed without a second readiness signal.
  • Never use code presence alone to override an open tracker dependency.
Rules / documentation

Remove volatile delivery status from durable instructions

  • Keep architecture and stable dependency intent in the Wiki.
  • Use issue relationships plus the Project for live work state.
  • Delete statements such as “Only RUS-01 should be planned now” and enumerated “RUS-06+ remains unimplemented” claims, or generate them from tracker state.
  • State one precedence rule in AGENTS.md: native open blockers determine readiness; readiness labels do not exist.
Workflow handoff

Close the loop at merge

  • Require ticket PRs to include Fixes #N so merge reliably closes the implemented issue.
  • Closing the issue automatically changes downstream derived readiness because the blocker is no longer open.
  • Manually close the linked issue when a PR was merged without the closing keyword.

Recommended state model

One fact, two derived views

Fact: native issue relationships and open/closed state.

Readiness: derived on demand; no duplicate labels.

Execution state: Project Todo/In Progress/Done, with GitHub's built-in close automation retained.

Stop maintaining parallel truth

Do not independently encode “what is ready now” in labels, issue prose, Wiki prose, Project fields, and AGENTS.md. Every extra handwritten copy creates another required transition and another stale gate.

Why this primitive fits

This is a deterministic relationship model, so native GitHub issue dependencies are the best primary primitive. No custom Action, AI subagent, MCP server, or probabilistic judgment is needed. The skill change remains valuable for legacy prose-only dependencies. A shell hook is the wrong boundary: readiness changes when a blocker closes, not during a particular local command.
